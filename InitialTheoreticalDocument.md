## **Initial theorical document for the systematic use of AI agents for user interface development**

---

### **1\. General Objective**

Action plan for the systematic use of AI agents in the development of user interfaces. The final objective is to maximize automation and the use of AI throughout the entire front-end development process of an application, while guaranteeing product quality both from the user’s perspective and in the resulting code.  
 To achieve this, we must design a robust, contract-based system that provides AI with an environment in which it can operate reliably and sustainably over time.

---

### **2\. System Principles**

Before diving into the architecture, it is worth explaining that the system is based on the following fundamental principles:

**Single source of truth**  
 Each element of the system (tokens, components, rules, screens) must have a clear owner and a canonical place where it lives.

**Explicit and versionable contracts**  
 The relationships between design, code, and behavior must be defined in a declarative way and be consumable by AI.

**Separation of responsibilities by layers**  
 Each level of abstraction solves a different problem and must not mix concepts from other levels.

**Progressive automation**  
 The system must allow starting with semi-automatic processes and evolving toward near-total automation.

---

### **3\. Levels of Abstraction of the System**

To analyze the system we want to develop, it makes sense to split it into three clearly differentiated parts, which correspond to different levels of abstraction.

The first involves a Figma file containing tokens and components on the design side, and the Design System repository on the development side.

The second is a semantic layer for the use of components. These semantic rules can have diverse origins; for example, they may be defined by design (layout rules, spacing between components, responsive breakpoints, etc.), or they may be constraints of technical origin, such as those required to meet accessibility requirements.

The third involves a Figma file on the client side where application screens are defined, and the repository of a Sift application on the development side.

---

### **4\. Layer 1: Infrastructure**

**Figma → Design System**

Figma (Tokens and Components) → Design System (Tokens automatically imported from Figma and Components)

This is the layer that provides the infrastructure. In my view, the ideal process that provides the highest level of automation would look something like this:

#### **4.1 Ideal Process**

a) Well-defined tokens in Figma (Design owns the tokens). These tokens are correctly defined and used across all components. There are no hardcoded values. Tokens must be exportable using a tool such as Tokens Studio and follow a well-defined naming convention.

b) The Design System imports the tokens generated by Tokens Studio to apply changes in the code. This process may include automatic processing via a script of the Tokens Studio export to directly generate the code consumed by the design system.

c) Use of Figma’s Code Connect so that each Figma component is connected to its implementation in the code repository, along with property mapping. For this purpose, Figma provides the `@figma/code-connect` package, which offers direct integration with Storybook for React. Thanks to this, you get the following benefits:

1. Access to the code implementation from Figma. A link to the code component that implements it is shown, along with code snippets and real component properties.

2. Access to the Figma view from Storybook.

3. Full management capability from an AI model that can use Figma MCP to extract whatever design data it needs from Figma.

---

#### **4.2 Benefits of Reaching the Ideal DS State**

But let’s assume we already have our design system in that state of development. What benefits do we gain a priori?

We have a clear single source of truth. Tokens belong to Design and remain in Figma, although they can easily be exported to be consumed by code, even integrating the process into automated pipelines. Components are created in Figma, but once validated by design following some defined procedure, they move to live in code, and the Storybook page—which must be accessible to everyone—becomes the source of truth.

There is synchronization based on well-defined contracts between Figma and code, which mitigates inconsistency issues.

The creation of new components or the modification of existing ones should be exponentially simplified. An AI model with well-defined instructions and context should be able to do almost all the work in a largely automatic way.

Once automatic or semi-automatic processes for change management are defined, maintaining the design system should save us a great deal of time on both the design and development sides.

---

### **5\. Layer 2: Component Semantics**

This layer defines the effective rules of the system and is essential for the effective use of AI. It must declaratively and versionably include, in a format consumable by AI (JSON, MD, etc.), details about the following aspects:

- Component composition rules

- When each component should be used

- Layout constraints (grid, stacks, responsive rules)

- Common patterns (templates)

- Explicit antipatterns

---

### **6\. Layer 3: Application**

**Figma (Application Screens) → Application Repository**

The next level is that of application screens. At this level, Figma is involved, where design defines the screens, and each application repository, where the screen is implemented. The process of moving from design to implementation can be divided into two parts.

#### **6.1 Static Screen**

This refers to the structure of the screen with the different visual components. Starting from a design system in the state described above, and with the help of Figma MCP, this process should be highly automated for an AI model. This also includes defining the mapping between data coming from the server-side data model (accessible through GET calls to the various endpoints) and the information displayed on the screen.

#### **6.2 Dynamic Screen**

This is the functionality. The best way to define this part needs to be investigated, although my first approach would be to divide it into three systematically defined layers:

a) User events  
 b) Effects (API calls, navigation, etc.)  
 c) States

As glue and general context, use-case definitions or activity diagrams—or both—would be used. There is significant room for research and experimentation in this area to find the optimal format for AI processing. This section could also include a Jira ticket definition format that facilitates direct consumption by AI.

---

### **7\. Cross-Cutting Layer: Architecture**

Once these three layers are defined, we move on to another important element that cuts across all layers: the definition of all architectural aspects that help our AI assistant understand every detail of how it should carry out implementation at each step.

It is very important to create a detailed definition that models all architectural decisions that must be made at every level of abstraction, along with the tools and the technology stack.  
 This provides our AI with a global context on which to base all its decisions.
